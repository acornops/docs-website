---
title: "Admin operations"
description: "Configure and use the control-plane admin API safely"
---

The control-plane admin API is for authorized self-host operators who need
break-glass or support workflows. It is disabled by default and is served under:

```text
https://api.example.com/admin/v1
```

Replace `example.com` with your deployment domain. Only enable it when you have a process for storing admin tokens and auditing
their use. Only the API host routes `/admin`. The management console host must
not proxy admin endpoints, and ordinary workspace sessions are not admin credentials. The platform admin console uses its internal BFF credential together with a separately authenticated platform-admin session.

## Enablement

For Kubernetes, enable the chart value and load token descriptors from the
platform Secret:

```yaml
adminApi:
  enabled: true
  ingress:
    enabled: true
  tokens:
    existingSecretName: acornops-platform-secrets
    tokensJsonKey: CONTROL_PLANE_ADMIN_TOKENS_JSON
```

For VM Compose:

```bash
CONTROL_PLANE_ADMIN_API_ENABLED=true
CONTROL_PLANE_ADMIN_TOKENS_JSON='[{"id":"ops-primary","name":"Ops primary","sha256":"<64 lowercase hex sha256>","scopes":["admin:*"],"enabled":true}]'
```

`CONTROL_PLANE_ADMIN_TOKENS_JSON` contains hash descriptors, not raw tokens.
Generate raw tokens out of band, store only the SHA-256 hash in the descriptor,
and deliver the raw token through your operator secret channel. Production
startup rejects enabled admin API configuration with no enabled token
descriptors, invalid hashes, duplicate ids, unsupported scopes, or placeholder
hash values.

## Auth and scopes

Every request uses:

```bash
curl -H "Authorization: Bearer $ACORNOPS_ADMIN_TOKEN" \
  https://api.example.com/admin/v1/me
```

Machine requests use named admin bearer tokens. Ordinary workspace cookies, internal service tokens, run-scoped JWTs and agent keys do not grant admin access. Human platform-admin requests retain their role, CSRF and recent-authentication checks through the admin console BFF. Scopes are separate from workspace roles.
Use the narrowest descriptor scopes possible:

```text
admin:self
admin:system:read
admin:audit:read
admin:workspace:read
admin:workspace:write
admin:workspace:policy:read
admin:workspace:plan:write
admin:workspace:external-hold:write
admin:user:read
admin:user:write
admin:member:write
admin:target:read
admin:target:write
admin:agent-key:rotate
admin:tooling:write
admin:run:read
admin:run:write
admin:*
```

## Mutations and audit

Mutating admin requests require a `reason`:

```bash
curl -X POST \
  -H "Authorization: Bearer $ACORNOPS_ADMIN_TOKEN" \
  -H "Content-Type: application/json" \
  -d '{"reason":"incident INC-1234: revoke stale browser sessions"}' \
  https://api.example.com/admin/v1/users/<user-id>/sessions/revoke
```

Each mutation writes an admin audit event. Workspace-scoped mutations also write
workspace audit events with `actor.type=admin_token` and the admin token id.
Audit metadata is sanitized and must not contain raw tokens, prompts, message
bodies, authorization headers, full tool arguments, or agent keys.

The target credential endpoint is the only admin response that returns target
bootstrap secret material:

```bash
curl -X POST \
  -H "Authorization: Bearer $ACORNOPS_ADMIN_TOKEN" \
  -H "Content-Type: application/json" \
  -d '{"reason":"rotate leaked target bootstrap key"}' \
  https://api.example.com/admin/v1/targets/<target-id>/agent-key/rotate
```

For Kubernetes targets, the replacement AgentK key is returned once. For VM
targets, the same administrative action returns a 15-minute one-use AgentV
replacement enrollment command and never returns the durable AgentV
credential. Both responses use `Cache-Control: no-store`.

## Workspace plans and quotas

Configure deployment-wide workspace plans in Kubernetes:

```yaml
workspacePlans:
  defaultPlanKey: default
  plans:
    - key: default
      name: Default
      quotas:
        members: 100
        kubernetesClusters: 30
        virtualMachines: 30
```

For VM Compose, set the equivalent `WORKSPACE_PLANS_CONFIG_JSON`.

Admins can change a workspace plan or set nullable quota overrides through
`PATCH /admin/v1/workspaces/{workspaceId}/plan` and
`PATCH /admin/v1/workspaces/{workspaceId}/quotas`. The control plane rejects
changes that would place current workspace usage over the resulting effective
limit unless you explicitly select `overLimitBehavior: "retain_existing"`. Plan changes preserve explicit resource overrides. Execution limits are configured per plan, with five independent pools; see [Workspace execution capacity](/deploy/workspace-capacity).


## Workspace suspension holds

A workspace can have one administrative hold and one external hold. Either hold suspends access. Clearing your hold does not clear the other, and the original suspension time remains while access stays blocked. Suspension cancels queued work and requests cancellation of executing work; restore never replays cancelled attempts.

Private administrative reasons remain in administrative records. Members receive only the public suspension message and minimal workspace identity. Narrow external controllers must explicitly use `source: "external"`; the admin console manages `source: "admin"`.

Machine policy changes require `requestId` and `expectedPolicyVersion`. Any caller supplying a request ID must also supply a version. Legacy broad callers may omit both. Retrying an unchanged request returns its original outcome for 30 days. After a version conflict, read current policy before submitting a new request.
